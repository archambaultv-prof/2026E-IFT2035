# Rust et la gestion semi-automatique

## Motivation

La gestion manuelle (C) est source intarissable de bogues graves. La gestion
automatique (GC) résout les bogues, mais introduit des pauses imprévisibles,
une consommation mémoire plus élevée, et nécessite que tout le système soit
conçu autour du GC.

**Peut-on avoir les deux à la fois ?** Sûreté mémoire sans GC, performances
équivalentes à C, détection des erreurs à la compilation plutôt qu'à
l'exécution ?

Rust est le premier langage populaire à proposer une réponse satisfaisante.
Il **permet au programmeur de contrôler explicitement la désallocation**, mais
**vérifie statiquement** — au moment de la compilation — que ces désallocations
sont correctes.

## Documentation disponible

Pour en apprendre plus sur Rust, consultez la [documentation
officielle](https://www.rust-lang.org/learn) et le [Rust
Book](https://doc.rust-lang.org/book/).

## Rust et Haskell

Rust est parfois décrit comme un mélange entre C et Haskell :

| Hérité de C | Hérité de Haskell |
|---|---|
| Langage de bas niveau | Encourage l'immuabilité |
| Gestion mémoire explicite | Types algébriques |
| Références explicites | Typage statique fort |
| Performances | Traits (classes de types) |

### Struct — l'équivalent des types produits

En Haskell, un type produit se définit avec `data` et un seul constructeur :

```haskell
data Point = Point Double Double
```

En Rust, l'équivalent est une **structure** (`struct`) avec des champs nommés :

```rust
struct Point {
    x: f64,
    y: f64,
}

fn main() {
    let p = Point { x: 1.0, y: 2.5 };
    println!("({}, {})", p.x, p.y);
}
```

### Enum — l'équivalent des types somme

En Haskell, un type somme se définit avec plusieurs constructeurs pouvant
porter des données :

```haskell
data Forme = Cercle Double | Rectangle Double Double

aire :: Forme -> Double
aire (Cercle r)      = pi * r * r
aire (Rectangle l h) = l * h
```

En Rust, l'équivalent est une **énumération** (`enum`). Comme en Haskell, les
variantes peuvent porter des données, et l'opérateur `match` joue le rôle du
filtrage par motif :

```rust
enum Forme {
    Cercle(f64),
    Rectangle(f64, f64),
}

fn aire(f: &Forme) -> f64 {
    match f {
        Forme::Cercle(r)       => std::f64::consts::PI * r * r,
        Forme::Rectangle(l, h) => l * h,
    }
}
```

La bibliothèque standard de Rust définit deux `enum` fondamentaux qui
correspondent directement à `Maybe` et `Either` de Haskell :

| Rust | Haskell | Rôle |
|---|---|---|
| `Option<T>` | `Maybe a` | Valeur optionnelle (présente ou absente) |
| `Result<T, E>` | `Either e a` | Succès ou erreur |


## Ownership — la propriété

Le mécanisme central de Rust est le système d'**ownership** (propriété).
Les règles sont simples :

1. Chaque valeur a **exactement un propriétaire** à la fois.
2. Quand le propriétaire **sort de portée**, la valeur est automatiquement
   désallouée.
3. La propriété peut être **transférée** (*moved*), mais pas dupliquée.

```rust
fn main() {
    let s1 = String::from("hello");  // s1 est propriétaire de la chaîne
    let s2 = s1;                     // la propriété est transférée à s2
    // println!("{}", s1);           // ERREUR : s1 n'est plus valide !
    println!("{}", s2);              // ok
}   // s2 sort de portée : la chaîne est désallouée ici
```

Le compilateur Rust rejette le programme si on tente d'utiliser `s1` après le
transfert. La chaîne est désallouée automatiquement à la fin de la portée de
`s2` — sans GC, sans `free` explicite.

### Comparaison avec C

```c
/* En C : le compilateur ne vérifie rien */
char* s1 = malloc(6);
strcpy(s1, "hello");
char* s2 = s1;    /* s1 et s2 pointent vers le même bloc */
free(s1);
free(s2);         /* double free — comportement indéfini ! */
```

En C, le compilateur autorise ce code. En Rust, le système d'ownership rend
ce scénario impossible par construction.

### Transfert vers une fonction

Passer une valeur à une fonction **transfère** la propriété à cette fonction.
L'appelant ne peut plus utiliser la valeur.

```rust
fn afficher(s: String) {
    println!("s = {}", s);
}   // s sort de portée ici : la chaîne est désallouée

fn main() {
    let s = String::from("hello");
    afficher(s);             // transfert de propriété à afficher
    // println!("{}", s);   // ERREUR : s n'est plus valide
}
```

## Le trait `Copy`

Certains types, comme les entiers et les flottants, sont si simples (taille
fixe, pas de pointeurs internes) que les copier est trivial et peu coûteux.
Pour ces types, Rust effectue une **copie silencieuse** au lieu d'un transfert :

```rust
fn main() {
    let x1 = 16;
    let x2 = x1;              // copie (pas de transfert)
    println!("{}", x1 + x2);  // x1 est toujours valide : 32
}
```

Un type implémente le trait `Copy` si et seulement s'il peut être copié par
simple copie bit à bit. Les types qui possèdent des ressources (comme `String`,
qui alloue sur le tas) n'implémentent **pas** `Copy`, car une copie naïve
créerait deux propriétaires du même bloc mémoire.

## Borrowing — emprunter sans transférer

Transférer la propriété à chaque appel de fonction est souvent trop restrictif.
Rust offre les **références** (*borrows*) pour permettre l'accès à une valeur
sans en prendre la propriété.

```rust
fn afficher(s: &String) {        // prend une référence (emprunt)
    println!("s = {}", s);
}   // la référence expire ici, mais s n'est PAS désallouée

fn main() {
    let s = String::from("hello");
    afficher(&s);                // prête s sans transférer la propriété
    println!("{}", s);           // s est encore valide !
}
```

L'opérateur `&` crée une référence vers la valeur. La fonction `afficher`
*emprunte* `s` le temps de son exécution : elle peut lire la valeur, mais pas
en prendre la propriété ni la désallouer.

### Références mutables

Par défaut, les références sont **en lecture seule**. Pour modifier la valeur
empruntée, on utilise une **référence mutable** `&mut T` :

```rust
fn doubler(v: &mut Vec<i32>) {
    v.push(42);   // modification autorisée via &mut
}

fn main() {
    let mut nombres = vec![1, 2, 3];
    doubler(&mut nombres);
    println!("{:?}", nombres);   // [1, 2, 3, 42]
}
```

### Règles du borrowing

Le système d'ownership impose des règles strictes sur les références pour
éviter les bogues d'alias :

| Règle | Signification |
|---|---|
| Plusieurs `&T` simultanées | Autorisé — plusieurs lecteurs en même temps |
| Une seule `&mut T` à la fois | Une seule écriture à la fois |
| Pas de `&mut T` et `&T` en même temps | Pas de lecteur pendant une écriture |

```rust
let mut s = String::from("hello");

let r1 = &s;       // ok — première référence en lecture
let r2 = &s;       // ok — deuxième référence en lecture
// let r3 = &mut s;  // ERREUR : on ne peut pas écrire quand on lit

println!("{} {}", r1, r2);  // r1 et r2 utilisées ici, puis expirées

let r3 = &mut s;   // ok maintenant — r1 et r2 ont expiré
r3.push_str(", world");
```

Ces règles éliminent toute une famille de bogues liés aux **alias** : deux
pointeurs qui désignent le même objet et dont l'un modifie l'objet pendant
que l'autre le lit.

## Slices — références sur des sous-tableaux

Au lieu de pointer au milieu d'un tableau avec de l'arithmétique de pointeurs
(comme en C), Rust offre les **slices** — des références portant à la fois un
pointeur et une longueur.

```rust
fn main() {
    let s = String::from("Hello, world");
    let sub: &str = &s[0..5];   // slice sur les 5 premiers octets
    println!("{}", sub);         // Hello
}
```

Le type `&str` (*string slice*) est une référence sur une sous-chaîne. Il
contient un pointeur vers le début et la longueur de la tranche — impossible
de déborder sans que le compilateur ou le runtime ne le détecte.

### Slices et invalidation

Une slice maintient un **emprunt actif** sur la valeur source. Tant que la
slice existe, le propriétaire ne peut pas modifier ni détruire la valeur —
le compilateur l'interdit statiquement.

```rust
fn main() {
    let mut notes = vec![15, 12, 18, 9, 14];
    let top: &[i32] = &notes[0..3];   // emprunte notes en lecture

    // notes.sort();   // ERREUR : notes est emprunté en lecture par top
                       // sort() requiert &mut notes
    println!("Top 3 : {:?}", top);   // ok
}
```

En C, l'équivalent compilait sans avertissement et le pointeur devenait fou
dès que le tableau était réalloué ou modifié. Rust détecte le problème
statiquement, à la compilation.

:::info[`&str` vs `String`]
Rust distingue deux types de chaînes :

| Type | Nature | Allocation |
|---|---|---|
| `String` | Chaîne possédée, modifiable | Tas |
| `&str` | Slice empruntée, lecture seule | Pointe vers `String`, littéral ou autre |

Les fonctions qui n'ont besoin que de *lire* une chaîne acceptent `&str` :
elles fonctionnent aussi bien avec une `&String` (Rust coerce automatiquement)
qu'avec un littéral `"bonjour"` stocké dans la zone statique.
:::

## Éviter les références folles

En C, retourner un pointeur vers une variable locale est un bogue classique.
Rust le rend impossible à la compilation :

```rust
fn dangereux() -> &String {
    let s = String::from("Hello");
    &s   // ERREUR : s est désalloué à la fin de la fonction !
}        // Rust refuse de compiler ce code
```

Pour retourner la valeur, on transfère la propriété (en retournant `String`
plutôt que `&String`) :

```rust
fn correct() -> String {
    let s = String::from("Hello");
    s   // transfert de propriété — la valeur survit à la fonction
}
```

## Lifetimes — durées de vie explicites

Lorsque plusieurs références ont des durées de vie différentes, le compilateur
doit vérifier qu'aucune référence ne survit à l'objet qu'elle désigne. Dans
les cas simples, Rust infère les lifetimes automatiquement. Dans
les cas ambigus, le programmeur doit les annoter explicitement.

:::info[Les lifetimes ne sont pas une nouveauté conceptuelle]
Les lifetimes existent implicitement dans tout programme C — le compilateur C
ne les vérifie simplement pas. Le programmeur doit s'assurer manuellement
qu'un pointeur ne survit pas à l'objet qu'il désigne. Rust rend cette
contrainte explicite et la vérifie automatiquement.
:::

Quand Rust ne peut pas inférer les lifetimes seul, le programmeur les annote
avec une **variable de lifetime** dont le nom commence par une apostrophe :
`'a`, `'b`, etc. Ces variables s'écrivent dans les chevrons génériques et
précèdent le type pointé dans chaque référence :

```rust
fn identite<'a>(x: &'a str) -> &'a str { x }
```

### Ce que `'a` signifie réellement

Une annotation de lifetime comme `'a` ne désigne pas une durée de vie fixe et
prédéterminée. C'est une **variable** que le compilateur instancie à chaque
appel : `'a` sera remplacé par l'**intersection** (le minimum) des durées de
vie des références concrètes passées à l'appel.

```rust
// Le compilateur ne sait pas si la valeur retournée provient de x ou de y.
// Il doit donc garantir que le résultat est valide aussi longtemps que
// les DEUX sources sont valides — d'où l'annotation commune 'a.
fn plus_longue<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let s1 = String::from("longue chaîne");   // lifetime : toute la fonction
    let resultat;
    {
        let s2 = String::from("xy");           // lifetime : bloc intérieur
        resultat = plus_longue(&s1, &s2);
        println!("{}", resultat);  // ok — utilisé avant la fin de s2
    }                              // s2 désalloué ici
    // println!("{}", resultat);  // ERREUR : s2 n'existe plus,
                                  // resultat pourrait pointer vers s2
}
```

Dans cet appel, `'a` est instancié avec le *minimum* des durées de vie de `s1`
et `s2`, c'est-à-dire la durée du bloc intérieur. Le compilateur refuse donc
d'utiliser `resultat` en dehors de ce bloc.

### Plusieurs paramètres de lifetime distincts

Quand deux paramètres ont des durées de vie **indépendantes** et que la valeur
de retour ne dépend que de l'un d'eux, on peut utiliser deux variables
distinctes `'a` et `'b` :

```rust
// Le résultat provient toujours de x — sa lifetime est 'a,
// indépendante de 'b (la lifetime de y).
fn premier<'a, 'b>(x: &'a str, _y: &'b str) -> &'a str {
    x
}
```

Par contre, dès que la valeur de retour **peut provenir de l'un ou l'autre**
des paramètres selon une condition connue seulement à l'exécution, le
compilateur exige que les deux lifetimes soient **unifiées** : il ne peut pas
savoir à l'avance laquelle sera effectivement retournée, il doit donc
garantir que les deux sources sont valides au moins aussi longtemps que le
résultat.

### Élision des lifetimes

Rust applique des **règles d'élision** qui permettent d'omettre les annotations
dans les cas les plus courants. Par exemple, une fonction à un seul paramètre
de référence n'a pas besoin d'annotation :

```rust
fn extraire<'a>(s: &'a str) -> &'a str { /* … */ }   // explicite
fn extraire(s: &str)        -> &str    { /* … */ }   // équivalent avec élision
```

Les deux signatures sont strictement équivalentes. Les règles d'élision sont :

1. Chaque paramètre de référence reçoit une lifetime distincte.
2. S'il n'y a qu'**un seul** paramètre de référence en entrée, sa lifetime
   est appliquée à toutes les références en sortie.
3. Si l'un des paramètres est `&self` ou `&mut self`, la lifetime de `self`
   est appliquée aux références en sortie.

Quand aucune règle ne s'applique (plusieurs paramètres de référence, pas de
`self`), l'annotation est **obligatoire**.

## Références dans les structures

Lorsqu'une structure contient une référence (plutôt que de posséder la valeur),
le compilateur doit savoir combien de temps la référence est valide. Sans
annotation, il ne peut pas vérifier que la structure ne survit pas à l'objet
qu'elle référence.

```rust
// ERREUR : lifetime manquante — le compilateur refuse
struct Segment {
    donnees: &str,
}
```

La solution consiste à **paramétrer la structure par une lifetime** `'a`,
qui exprime que l'instance ne peut pas survivre à la valeur empruntée :

```rust
struct Segment<'a> {
    donnees: &'a str,
}

fn main() {
    let texte = String::from("rust est sûr");
    let seg = Segment { donnees: &texte[0..4] };  // seg emprunte texte
    println!("{}", seg.donnees);                  // "rust"
}   // seg désalloué avant texte — ordre correct
```

Tenter de stocker `seg` dans une portée plus large que `texte` est refusé à
la compilation. L'alternative est de faire en sorte que la structure
**possède** la donnée (avec `String` plutôt que `&str`), ce qui évite les
annotations mais implique une copie de la valeur.

:::tip[Quand utiliser des références dans une structure ?]
Favoriser la possession (`String`, `Vec<T>`) pour les structures à longue
durée de vie. Les références conviennent aux structures éphémères (vues,
itérateurs) dont la durée de vie est clairement délimitée.
:::

## `Box<T>` — allocation sur le tas et types récursifs

`Box<T>` est le type fondamental pour allouer une valeur **sur le tas** en
Rust. C'est un pointeur unique, propriétaire de la valeur pointée. Quand le
`Box` sort de portée, la valeur sur le tas est automatiquement désallouée —
aucun `free` explicite.

```rust
fn main() {
    let b: Box<i32> = Box::new(42);   // 42 est alloué sur le tas
    println!("{}", *b);               // déréférencement : 42
}   // b sort de portée : la mémoire est libérée ici
```

Contrairement à un `malloc` en C, `Box::new` ne peut pas retourner un
pointeur nul et la taille allouée est toujours exactement `sizeof(T)`.

### Types récursifs

La principale utilisation de `Box` en pratique est de permettre la définition
de **types récursifs** — des types dont la taille dépend d'eux-mêmes.

Considérons un arbre binaire d'entiers. La définition naïve est invalide :

```rust
// ERREUR : la taille d'Arbre est infinie —
// un Noeud contient deux Arbre, qui contiennent chacun deux Arbre…
enum Arbre {
    Feuille(i32),
    Noeud(Arbre, Arbre),
}
```

Le compilateur doit connaître la taille d'`Arbre` à la compilation pour
réserver l'espace sur la pile — mais cette taille est infinie.

Avec `Box<Arbre>`, chaque branche est un **pointeur** vers un arbre sur le
tas. La taille d'un pointeur est fixe (8 octets sur 64 bits), ce qui brise
la récursion infinie :

```rust
// CORRECT : Box<Arbre> a une taille fixe (un pointeur)
enum Arbre {
    Feuille(i32),
    Noeud(Box<Arbre>, Box<Arbre>),
}

fn main() {
    //       (5)
    //      /   \
    //    (3)   (8)
    let arbre = Arbre::Noeud(
        Box::new(Arbre::Feuille(3)),
        Box::new(Arbre::Feuille(8)),
    );
}   // arbre désalloué ici : les Box imbriqués sont libérés récursivement
```

Representation mémoire :

```
Pile :
  arbre = Noeud { gauche: 0x..., droite: 0x... }

Tas :
  [0x...] = Feuille(3)
  [0x...] = Feuille(8)
```

Le même mécanisme s'applique à toute structure de données récursive : listes
chaînées, arbres n-aires, etc.

## Contrôle de la mutabilité

L'ownership contrôle aussi les **mutations** pour éviter les bogues d'alias.
Dès qu'une référence immuable est active sur une valeur, toute opération qui
nécessiterait `&mut` est bloquée par le compilateur :

```rust
let mut s = String::from("bonjour");
let debut = &s[0..3];           // emprunt en lecture : "bon"

// s.push_str(" monde");        // ERREUR : s est déjà emprunté en lecture
                                // push_str requiert &mut s
println!("{}", debut);          // ok
```

En C, un pointeur `char*` vers le milieu d'une chaîne réallouée devient
silencieusement invalide. Rust rend ce scénario impossible par construction.

## Résumé

| Aspect | C (manuel) | GC (automatique) | Rust (semi-automatique) |
|---|---|---|---|
| Qui libère | Le programmeur | Le GC | Le compilateur (au moment où le propriétaire sort de portée) |
| Fuites possibles ? | Oui | Non | Non |
| Pointeurs fous possibles ? | Oui | Non | Non |
| Pauses GC | Non | Oui | Non |
| Détection des erreurs | À l'exécution | À l'exécution | À la compilation |
| Courbe d'apprentissage | Faible | Faible | Élevée |
