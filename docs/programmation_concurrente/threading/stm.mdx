# Mémoire transactionnelle logicielle (STM) en Haskell

Dans la section sur l'[atomicité](atomicite.mdx), nous avons vu qu'il est
difficile de composer des opérations concurrentes de façon correcte avec des
verrous explicites. Haskell propose une solution radicalement différente : la
**mémoire transactionnelle logicielle** (*Software Transactional Memory*, STM).

## Actions IO

Haskell est un langage **pur** : une fonction ne peut pas avoir d'effets de
bord (modifier une variable, afficher à l'écran, etc.). Pour exprimer des
effets, Haskell utilise le type `IO`. Une valeur de type `IO a` représente une
**action** qui, quand elle est exécutée, produit une valeur de type `a` et peut
avoir des effets.

```haskell
-- putStrLn prend une chaîne et retourne une action IO qui n'a pas de résultat
putStrLn :: String -> IO ()

-- readLn lit une ligne et retourne une action IO produisant un Int
readLn :: IO Int
```

## La notation do

Pour enchaîner des actions `IO`, Haskell utilise la notation `do`. C'est
l'équivalent d'une séquence d'instructions impératives :

```haskell
-- Équivalent Python :
-- print("Quel est votre nom ?")
-- nom = input()
-- print("Bonjour, " + nom)

main :: IO ()
main = do
    putStrLn "Quel est votre nom ?"
    nom <- getLine          -- <- récupère le résultat de l'action
    putStrLn ("Bonjour, " ++ nom)
```

- `<-` est l'équivalent de `=` pour récupérer le résultat d'une action `IO`.
- `let` (sans `in`) dans un bloc `do` lie une valeur pure (sans effets).

```haskell
main :: IO ()
main = do
    let x = 2 + 2      -- calcul pur, pas d'action IO
    print x             -- affiche 4
```

## forkIO — créer un thread

La fonction `forkIO` crée un nouveau thread qui exécute une action `IO` :

```haskell
import Control.Concurrent (forkIO, threadDelay)

main :: IO ()
main = do
    forkIO $ do
        threadDelay 1000000   -- attendre 1 seconde (en microsecondes)
        putStrLn "Thread secondaire"
    putStrLn "Thread principal"
    threadDelay 2000000       -- attendre 2 secondes pour que le thread secondaire ait le temps de s'exécuter
```

En Haskell, quand le thread principal se termine, le programme s'arrête
immédiatement — même si des threads secondaires sont encore en cours
d'exécution. Sans le `threadDelay` final, le programme se terminerait avant
que le thread secondaire n'ait le temps d'afficher son message.

`threadDelay` prend un nombre de **microsecondes** (1 000 000 = 1 seconde).

---

## Pourquoi STM ?

Revenons au problème du transfert bancaire. En Python, même avec des verrous
sur chaque méthode, composer `retrait` et `depot` en une opération atomique
exigeait d'exposer des détails internes ou d'utiliser une hiérarchie précise de
verrous.

STM propose une approche différente : vous **décrivez** ce que vous voulez
faire de façon atomique, et le système s'occupe de la synchronisation. Si deux
threads entrent en conflit, l'un est automatiquement **annulé et relancé**,
sans deadlock possible.

---

## Les types fondamentaux de STM

STM en Haskell repose sur trois concepts :

| Concept | Type Haskell | Description |
|---------|--------------|-------------|
| Variable partagée | `TVar a` | Une variable mutable accessible depuis plusieurs threads |
| Action transactionnelle | `STM a` | Une action qui s'exécute à l'intérieur d'une transaction |
| Exécution atomique | `atomically :: STM a -> IO a` | Lance une transaction et la rend atomique |

### TVar — variable transactionnelle

Une `TVar a` est une variable mutable de type `a` qui ne peut être lue et
modifiée qu'à l'intérieur d'une transaction STM.

```haskell
import Control.Concurrent.STM

-- Créer une TVar contenant l'entier 0
creerCompteur :: IO (TVar Int)
creerCompteur = newTVarIO 0
--              ^^^^^^^^^ crée une TVar dans IO (hors transaction)
```

Pour lire et écrire une `TVar`, on utilise les fonctions suivantes **à
l'intérieur d'un bloc STM** :

```haskell
readTVar  :: TVar a -> STM a        -- lire la valeur
writeTVar :: TVar a -> a -> STM ()  -- écrire une nouvelle valeur
modifyTVar :: TVar a -> (a -> a) -> STM ()  -- modifier avec une fonction
```

### atomically — rendre une transaction atomique

`atomically` prend une action `STM` et l'exécute comme une transaction atomique
dans `IO` :

```haskell
atomically :: STM a -> IO a
```

Tout ce qui se passe dans `atomically` est :
- **Atomique** : vu en une seule fois par les autres threads
- **Cohérent** : les invariants sont maintenus
- **Isolé** : les effets ne sont visibles qu'après la validation (*commit*)

## Premier exemple : un compteur

Voici l'équivalent Haskell/STM du compteur partagé, sans condition de course
et sans verrou explicite :

```haskell
import Control.Concurrent       (forkIO, threadDelay)
import Control.Concurrent.STM   (TVar, newTVarIO, readTVar, modifyTVar, atomically)
import Control.Monad            (replicateM_)

-- Incrémenter le compteur nb_fois fois
incrementer :: TVar Int -> Int -> IO ()
incrementer compteur nb_fois =
    replicateM_ nb_fois $           -- répéter nb_fois fois
        atomically $                -- chaque incrément est atomique
            modifyTVar compteur (+1)

main :: IO ()
main = do
    compteur <- newTVarIO 0         -- créer le compteur à 0

    let nb_iterations = 10000
        nb_threads    = 4

    -- Lancer nb_threads threads
    threads <- mapM (\_ -> forkIO (incrementer compteur nb_iterations))
                    [1..nb_threads]

    threadDelay 2000000             -- attendre 2 secondes

    valeur_finale <- atomically (readTVar compteur)
    let attendu = nb_threads * nb_iterations
    putStrLn $ "Attendu : " ++ show attendu
    putStrLn $ "Obtenu  : " ++ show valeur_finale
    if valeur_finale == attendu
        then putStrLn "OK: Resultat correct !"
        else putStrLn "ERREUR: Resultat incorrect !"
```

Pas de `Lock`, pas de `with`, pas de risque d'oublier un verrou. Chaque appel
à `atomically` garantit que l'incrément est atomique.

:::note[Comparaison avec Python]
```python
# Python — verrou explicite requis
lock = threading.Lock()
def incrementer():
    with lock:
        compteur[0] += 1
```
```haskell
-- Haskell STM — atomicité déclarative
incrementer :: TVar Int -> STM ()
incrementer compteur = modifyTVar compteur (+1)
```
En Haskell, le type `STM ()` **force** l'appelant à envelopper l'appel dans
`atomically`. Oublier `atomically` est une erreur de compilation, pas un bug
silencieux.
:::

## Composer des opérations STM

C'est ici que STM brille vraiment. Les actions `STM` se **composent** avec la
notation `do`, exactement comme les actions `IO` :


```haskell
transfert :: TVar Int -> TVar Int -> Int -> STM Bool
transfert source destination montant = do
    solde_source <- readTVar source
    if solde_source < montant
        then return False
        else do
            modifyTVar source      (subtract montant)
            modifyTVar destination (+montant)
            return True
```

Pour l'exécuter :

```haskell
ok <- atomically (transfert compte_a compte_b 200)
```

Les deux `modifyTVar` s'exécutent **atomiquement** : aucun thread ne peut
observer un état où l'argent a quitté `source` sans être arrivé dans
`destination`. Le problème de la section précédente est résolu par
construction.

## Exemple complet : transfert bancaire

Voici le programme complet qui démontre que l'invariant est toujours respecté :

```haskell
import Control.Concurrent       (forkIO, threadDelay)
import Control.Concurrent.STM
import Control.Monad            (forever, when)
import Data.IORef               (IORef, newIORef, modifyIORef, readIORef)

-- Transfert atomique entre deux TVar
transfert :: TVar Int -> TVar Int -> Int -> STM Bool
transfert source destination montant = do
    s <- readTVar source
    if s < montant
        then return False
        else do
            modifyTVar source      (subtract montant)
            modifyTVar destination (+montant)
            return True

main :: IO ()
main = do
    compte_a <- newTVarIO 500
    compte_b <- newTVarIO 100
    let invariant = 600

    violations <- newIORef (0 :: Int)   -- compteur de violations
    observations <- newIORef (0 :: Int) -- compteur total d'observations

    -- Thread 1 : faire des transferts en boucle
    forkIO $ forever $ do
        atomically $ transfert compte_a compte_b 50
        atomically $ transfert compte_b compte_a 50

    -- Thread 2 : vérifier l'invariant en permanence
    forkIO $ forever $ do
        total <- atomically $ do
            a <- readTVar compte_a
            b <- readTVar compte_b
            return (a + b)
        modifyIORef observations (+1)
        when (total /= invariant) $
            modifyIORef violations (+1)

    -- Laisser tourner 1 seconde
    threadDelay 1000000

    v  <- readIORef violations
    n  <- readIORef observations
    let pct = fromIntegral v / fromIntegral n * 100 :: Double
    putStrLn $ "Observations : " ++ show n
    putStrLn $ "Violations   : " ++ show v
                ++ " (" ++ show (round pct :: Int) ++ "%)"
    if v == 0
        then putStrLn "OK: Invariant toujours respecte"
        else putStrLn "ERREUR: Invariant viole !"
```

Notez que la lecture de l'invariant est elle aussi dans un `atomically` :

```haskell
total <- atomically $ do
    a <- readTVar compte_a
    b <- readTVar compte_b
    return (a + b)
```

Les deux lectures forment une transaction atomique : on ne peut pas lire `a`
après le débit et `b` avant le crédit. C'est impossible avec des verrous par
compte en Python sans coordination supplémentaire.

---

## Résumé : STM vs verrous

| | Verrous (Python) | STM (Haskell) |
|---|---|---|
| Atomicité sur plusieurs variables | Manuel, sujet aux oublis | Automatique via `atomically` |
| Composition | Difficile (ordre des verrous) | Triviale (notation `do`) |
| Deadlock possible | Oui | Non (STM ne verrouille pas à l'avance) |
| Erreurs silencieuses | Oui (oubli d'un verrou) | Non (erreur de compilation) |
| Disponible en Python | — | Non (pas d'implémentation STM en production) |

STM ne remplace pas tous les besoins en concurrence, mais pour les données
partagées mutables avec des invariants à maintenir, c'est l'une des
abstractions les plus sûres et les plus expressives disponibles.

## Comment STM fonctionne-t-il ?

### Le journal de transaction

Quand un thread entre dans un `atomically`, STM crée un **journal de
transaction** local au thread. Ce journal enregistre toutes
les opérations effectuées sur les `TVar` pendant la transaction :

- Chaque `readTVar` note la valeur lue et la version de la `TVar` au moment de
  la lecture.
- Chaque `writeTVar` note la nouvelle valeur à écrire — mais **n'écrit rien
  encore en mémoire partagée**.


### La validation (commit)

À la fin du `atomically`, le runtime tente de **valider** la transaction :

1. **Vérification** : Pour chaque `TVar` lue, la version actuelle en mémoire
   est-elle la même que celle notée dans le journal ? Si un autre thread a
   modifié une `TVar` lue entre-temps, la transaction est **invalide**.
2. **Commit** : Si toutes les versions sont intactes, les nouvelles valeurs sont
   appliquées atomiquement à toutes les `TVar`.
3. **Rollback** : Si la vérification échoue, le journal est jeté et la
   transaction est relancée depuis le début.


Ce mécanisme s'appelle la **concurrence optimiste** : on suppose qu'il n'y a
pas de conflit, on travaille en local, et on vérifie seulement à la fin.

### Pourquoi rollback est-il sûr ?

C'est ici qu'intervient la **pureté de Haskell**. Une action de type `STM a`
ne peut faire **que** des lectures et écritures de `TVar` — c'est garanti par
le système de types. Elle ne peut pas afficher à l'écran, écrire dans un
fichier, ou modifier une structure de données en dehors des `TVar`.

Donc si on annule une transaction, il suffit de **jeter le journal** : il n'y a
aucun autre effet à annuler. C'est ce qui rend le rollback trivial.

## STM est-il une librairie ou fait-il partie du compilateur ?

La réponse est : **les deux, à des niveaux différents**.

- **L'API** (`TVar`, `STM`, `atomically`, `retry`, `orElse`) est définie dans
  le paquet `stm`, qui est une **librairie ordinaire** qu'on importe comme
  n'importe quelle autre.
- **Le mécanisme de commit atomique** repose sur des primitives du **runtime de
  GHC** (le compilateur Haskell). En particulier, la validation et l'écriture
  atomique de plusieurs `TVar` utilisent des instructions de bas niveau
  (compare-and-swap) que GHC expose à travers des opérations primaires
  internes.

En pratique, vous n'avez besoin de connaître que l'API. Mais il est utile de
savoir que `atomically` n'est pas de la "magie" : c'est une fonction ordinaire
dont l'implémentation interne utilise des opérations bas niveau du runtime.

## Pourrait-on écrire STM pour Python ?

**La mécanique du journal est faisable.** On pourrait créer une classe `TVar`
en Python, maintenir un journal thread-local, et implémenter un `atomically`
qui valide et commit.

**Mais le problème fondamental est la pureté.** En Python, rien n'empêche une
"transaction" de faire des effets de bord non capturés par le journal :

```python
# Python — rien n'empêche ceci dans une transaction
def transfert(source, destination, montant):
    if source.get() >= montant:
        source.set(source.get() - montant)
        print("argent débité")   # effet de bord hors journal !
        ma_liste.append(montant) # modification hors journal !
        destination.set(destination.get() + montant)
```

Si cette transaction est annulée et relancée à cause d'un conflit, `print` et
`ma_liste.append` auront déjà été exécutés. Le rollback ne peut pas les
défaire. La transaction ne serait donc pas vraiment atomique.

En Haskell, le type `STM a` **interdit** les actions `IO` à l'intérieur. Le
compilateur refuse ce code :

```haskell
-- ERREUR DE COMPILATION : putStrLn est IO, pas STM
transfert_invalide :: TVar Int -> TVar Int -> Int -> STM Bool
transfert_invalide source destination montant = do
    putStrLn "argent débité"  -- ← le compilateur rejette cette ligne
    ...
```

**Conclusion :** On pourrait écrire une STM partielle pour Python qui fonctionne
si les transactions n'ont pas d'effets de bord externes, mais le langage ne peut
pas l'*imposer*. En Haskell, le système de types le garantit statiquement — c'est
pour cela que STM y est vraiment sûr.
