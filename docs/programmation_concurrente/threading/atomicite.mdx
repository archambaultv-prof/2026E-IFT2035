# Atomicité

## Qu'est-ce que l'atomicité ?

Une opération est **atomique** si elle s'exécute entièrement ou pas du tout,
sans qu'aucun autre thread ne puisse observer un état intermédiaire. Du point de
vue des autres threads, une opération atomique est instantanée.

L'atomicité est une propriété **plus forte** que l'absence de course. On peut
avoir un programme sans condition de course qui n'est pourtant pas correct,
parce que plusieurs opérations consécutives ne forment pas un bloc atomique.

## Absence de course ≠ atomicité

Voici un exemple qui l'illustre : un compte bancaire avec ses propres verrous.

```python
import threading

class Compte:
    def __init__(self, solde_initial):
        self.solde = solde_initial
        self._lock = threading.Lock()

    def depot(self, montant):
        with self._lock:
            self.solde += montant

    def retrait(self, montant):
        with self._lock:
            if self.solde >= montant:
                self.solde -= montant
                return True
            return False

    def get_solde(self):
        with self._lock:
            return self.solde
```

Chaque méthode est protégée par un verrou : `depot`, `retrait` et `get_solde`
sont sans condition de course. Mais maintenant, essayons de **transférer** de
l'argent entre deux comptes :

```python
import threading
import time

def transfert(source, destination, montant):
    if source.retrait(montant):
        # ← État intermédiaire : l'argent a quitté `source` mais n'est pas
        #   encore dans `destination`. Un autre thread peut observer cet état.
        time.sleep(0.0001)  # Rend la fenêtre d'observation systématique
        destination.depot(montant)

compte_a = Compte(500)
compte_b = Compte(100)
INVARIANT = compte_a.get_solde() + compte_b.get_solde()  # 600
violations = []
stop = threading.Event()

def faire_transferts():
    """Thread qui effectue des transferts en boucle"""
    while not stop.is_set():
        transfert(compte_a, compte_b, 50)
        transfert(compte_b, compte_a, 50)

nb_observations = 0
violations = []

def verifier_invariant():
    """Thread qui vérifie que solde_a + solde_b == 600 en permanence"""
    global nb_observations
    while not stop.is_set():
        total = compte_a.get_solde() + compte_b.get_solde()
        nb_observations += 1
        if total != INVARIANT:
            violations.append(total)

t_transfert = threading.Thread(target=faire_transferts)
t_verification = threading.Thread(target=verifier_invariant)
t_transfert.start()
t_verification.start()

time.sleep(0.5)
stop.set()
t_transfert.join()
t_verification.join()

if violations:
    pourcentage = len(violations) / nb_observations * 100
    print(f"❌ {len(violations)} violation(s) sur {nb_observations} observations ({pourcentage:.1f}%)")
    print(f"   Exemple : total observé = {violations[0]} au lieu de {INVARIANT}")
else:
    print(f"✅ Aucune violation sur {nb_observations} observations (relancez le programme)")
```

Chaque opération (`retrait`, `depot`) est correcte individuellement — aucune
condition de course sur les variables — mais leur composition ne l'est pas.
Le thread de vérification observe régulièrement un total de 550 au lieu de 600 :
l'argent a quitté `compte_a` mais n'est pas encore arrivé dans `compte_b`.
L'**invariant global** (solde_a + solde_b = 600) est violé temporairement.

## La composition est difficile

### Tentative 1 : un verrou global autour des appels de méthodes

L'idée naturelle est d'entourer les deux appels d'un verrou externe :

```python
transfert_lock = threading.Lock()

def transfert(source, destination, montant):
    with transfert_lock:
        if source.retrait(montant):
            destination.depot(montant)
```

Cela fonctionne... à condition que **tout le code** qui accède à ces comptes
prenne aussi `transfert_lock`. Si `verifier_invariant` appelle `get_solde()`
sans ce verrou, il peut toujours observer un état intermédiaire. C'est facile
d'oublier d'acquérir le verrou global dans chaque point d'accès, et rien dans
le code ne l'impose.

### Tentative 2 : accéder aux attributs internes

Pour contourner le problème de ré-entrance (le verrou interne de `retrait` et
celui de `depot` sont distincts), on pourrait accéder directement aux attributs :

```python
def transfert(source, destination, montant):
    with transfert_lock:
        if source.solde >= montant:   # accès direct à l'attribut privé
            source.solde -= montant
            destination.solde += montant
```

Cela fonctionne, mais **brise l'encapsulation** : la fonction `transfert` doit
connaître les détails internes de `Compte`. Si l'implémentation de `Compte`
change, cette fonction casse.


### Solution robuste : ordonner l'acquisition des verrous

La vraie solution qui préserve l'encapsulation utilise deux techniques :

1. **`RLock`** (*reentrant lock*) : un thread peut acquérir le même verrou
   plusieurs fois sans se bloquer lui-même. Cela permet d'appeler `retrait` et
   `depot` de l'extérieur pendant qu'on tient déjà leur verrou.
2. **Ordre canonique d'acquisition** : toujours acquérir les verrous dans le
   même ordre (par exemple, par identifiant croissant) pour éviter les
   [deadlocks](./race_conditions_lock.mdx).

```python
import threading

class Compte:
    _next_id = 0

    def __init__(self, solde_initial):
        self.id = Compte._next_id
        Compte._next_id += 1
        self.solde = solde_initial
        self._lock = threading.RLock()  # RLock : ré-entrance autorisée

    def depot(self, montant):
        with self._lock:
            self.solde += montant

    def retrait(self, montant):
        with self._lock:
            if self.solde >= montant:
                self.solde -= montant
                return True
            return False

    def get_solde(self):
        with self._lock:
            return self.solde

def transfert(source, destination, montant):
    # Acquérir les deux verrous dans un ordre fixe pour éviter les deadlocks :
    # si deux threads font transfert(A→B) et transfert(B→A) en même temps,
    # les deux acquièrent d'abord le verrou du compte avec le plus petit id,
    # ce qui casse la symétrie qui causerait un deadlock.
    premier, second = sorted([source, destination], key=lambda c: c.id)
    with premier._lock:
        with second._lock:
            # Les deux comptes sont verrouillés simultanément.
            # RLock permet à retrait() et depot() d'acquérir _lock à nouveau.
            if source.retrait(montant):
                destination.depot(montant)
                return True
            return False
```

Cette approche est correcte et préserve l'encapsulation, mais elle expose
`_lock` à la fonction `transfert` (qui doit connaître l'existence du verrou
interne). En pratique, `transfert` serait une méthode de la même couche
d'abstraction que `Compte`.

:::note
Dans un vrai système de production gérant des données financières, on
n'utilise généralement pas des verrous manuels : on délègue à une **base de
données** qui offre des transactions ACID. C'est l'approche la plus fiable,
car le moteur de base de données gère lui-même l'atomicité, la cohérence et
l'isolation.
:::


## Le vrai défi : granularité

Le problème fondamental est la tension entre deux objectifs :

| Verrou trop **grossier** | Verrou trop **fin** |
|--------------------------|---------------------|
| Un seul verrou pour tout | Un verrou par variable |
| Atomicité facile à obtenir | Composition difficile |
| Peu de parallélisme | Beaucoup de parallélisme |
| Performances limitées | Risques de deadlock |

Il n'existe pas de solution universelle en Python avec des verrous. La bonne
granularité dépend du cas d'usage.

## Et dans d'autres langages ?

Certains langages proposent des mécanismes qui résolvent élégamment ce problème.

La **mémoire transactionnelle logicielle** (STM — *Software Transactional
Memory*), popularisée par Haskell (module `STM`), permet de définir des
**transactions** : des blocs de code qui s'exécutent de manière atomique sans
avoir à spécifier manuellement quels verrous prendre. Si deux transactions
entrent en conflit, l'une d'elles est automatiquement annulée et relancée
(*rollback*).
