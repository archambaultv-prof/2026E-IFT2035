# Portée et fermetures

## La portée d'une variable

La **portée** (*scope*) d'un nom est la région du programme où ce nom est
accessible. Comprendre la portée est essentiel pour savoir quelle valeur un
nom désigne à un endroit donné du code.

Dans l'exemple suivant, `x` est défini globalement, mais dans `g`, le paramètre
`x` *masque* le `x` global : à l'intérieur de `g`, `x` désigne l'argument reçu,
pas la valeur globale `10`.

```haskell
x = 10          -- x global vaut 10

f y = x + y     -- x ici désigne le x global = 10

g x = x * 2     -- ce x est le paramètre de g, pas le x global
                -- à l'intérieur de g, x désigne l'argument passé
```

On peut vérifier ce comportement dans GHCi :

```haskell
ghci> f 5    -- 10 + 5
15
ghci> g 3    -- 3 * 2
6
ghci> g x    -- g 10 = 10 * 2
20
```

## Portée statique vs portée dynamique

Il existe deux façons d'interpréter la portée d'une variable :

### Portée statique (lexicale)

La valeur d'un nom est déterminée par sa position dans le **texte du programme**
(*à la lecture du code*). C'est la portée de Haskell, Python, Java, OCaml et
la plupart des langages modernes.

Concrètement, cela signifie qu'on peut toujours déterminer ce que désigne un
nom en regardant simplement le code source, sans avoir à simuler l'exécution.
C'est pourquoi on dit que la portée est *lexicale* : elle correspond à la
structure du texte, et plus précisément à la structure de l'**arbre syntaxique
abstrait (AST)**. Un nom est résolu en remontant dans l'AST jusqu'au nœud
englobant le plus proche qui introduit ce nom (paramètre, `let`, `where`,
etc.).

Dans l'exemple ci-dessous, `afficherZoom` capture la valeur de `zoom` telle
qu'elle est définie *au moment de sa définition* — le `zoom = 999` défini plus
tard dans un `let` ne change rien.

```haskell
zoom = 100

afficherZoom = zoom     -- zoom est résolu au moment de la définition
                        -- → afficherZoom = 100

local = let zoom = 999 in afficherZoom
-- Même si on crée un zoom local à 999, afficherZoom utilise
-- toujours le zoom de sa définition = 100
```

```haskell
ghci> local
100
```


### Portée dynamique

La valeur d'un nom est déterminée par l'environnement **au moment de
l'exécution**. Certains langages anciens (L'ancien dialect de Emacs Lisp, Shell bash pour les
variables d'environnement) utilisent ce modèle.

Avec la portée dynamique, le programme ne cherche pas où un nom a été défini
dans le texte, mais quel nom du même identifiant est *actif* au moment de
l'appel. Avec portée dynamique, `local` ci-dessus retournerait `999` car
`zoom = 999` est la définition active sur la pile d'appels au moment de
l'exécution de `afficherZoom`.

:::note
La portée dynamique est source de nombreux bogues subtils car le comportement
d'une fonction dépend du contexte d'appel, ce qui viole la transparence
référentielle. Les langages modernes préfèrent généralement la portée statique.
:::


## Portée des blocs et définitions locales

Les langages diffèrent sur une question pratique importante : est-ce qu'une
structure de contrôle (`if`, `for`, `while`) ou un bloc de code introduit une
nouvelle portée ? La réponse varie selon le langage et a des conséquences
directes sur la visibilité des noms définis à l'intérieur.

En Haskell, `let` et `where` introduisent toujours une portée **strictement
locale** : les noms définis à l'intérieur ne sont visibles qu'à l'intérieur de
l'expression ou de la fonction qui les contient. Cela permet de nommer des
calculs intermédiaires sans polluer l'espace de noms global.

```haskell
f x =
  let a = x + 1
      b = a * 2    -- a est visible ici
  in  a + b        -- a et b sont visibles ici
-- a et b ne sont pas visibles en dehors de f

g x = résultat
  where
    résultat = intermédiaire * 2
    intermédiaire = x + 10    -- les définitions where se voient entre elles
```

Notez que les définitions dans un même bloc `let` ou `where` sont toutes
mutuellement visibles : `b` peut utiliser `a`, et `résultat` peut utiliser
`intermédiaire`, peu importe l'ordre d'écriture. Les définitions `where` et
`let` peuvent même être **mutuellement récursives** — une définition peut
référencer l'autre.


Toutefois, comme mentionné, le comportement varie selon les langages. En **Python**, les structures de
contrôle (`if`, `for`, `while`) ne créent **pas** de nouvelle portée : une
variable définie à l'intérieur reste visible à l'extérieur.

```python
if True:
    x = 42      # x est défini dans le if...

print(x)        # ...mais visible ici ! → 42
```

```python
for i in range(5):
    resultat = i * 2

print(resultat)  # visible ici aussi → 8
print(i)         # même i est visible → 4
```

En **Java** (et C, C++), les accolades `{}` créent une portée stricte : toute
variable déclarée dans un bloc `{}` n'est pas visible à l'extérieur.

```java
if (true) {
    int x = 42;   // x est local au bloc if
}
System.out.println(x);  // ERREUR : x n'existe pas ici
```

Il n'y a pas de surprise : les noms intermédiaires ne « s'échappent » jamais
hors de leur bloc.


## Ombrage de noms (*shadowing*)

Un nom local peut **masquer** (*shadow*) un nom externe portant le même nom.
Cela se produit lorsqu'un paramètre, un `let` ou un `where` introduit un
identifiant qui existe déjà dans une portée plus large. Le nom local prend
alors priorité à l'intérieur de sa portée.

```haskell
valeur = 42

f valeur = valeur + 1    -- ce `valeur` est le paramètre, pas le global
```

Dans le corps de `f`, `valeur` désigne le paramètre, pas la valeur globale `42`.
On peut s'en convaincre dans GHCi :

```haskell
ghci> f 10    -- 10 + 1 (pas 42 + 1)
11
ghci> f valeur    -- f 42 = 42 + 1
43
```

En Haskell (portée statique), le `valeur` dans le corps de `f` désigne
**toujours** le paramètre, même si le global existe aussi. Ce comportement est
prévisible : il suffit de regarder la définition de `f` pour savoir quel `valeur`
est utilisé, sans tenir compte du contexte d'appel.


## Variables libres et variables liées

Dans une expression, une **variable liée** est un nom introduit localement
(paramètre, `let`, `where`, pattern). Une **variable libre** est un nom
qui vient de l'extérieur — elle n'est pas introduite par l'expression elle-même,
mais capturée depuis la portée englobante.

Cette distinction est fondamentale pour comprendre les fermetures : une
fermeture, c'est précisément une fonction qui contient des variables libres et
qui les capture au moment de sa définition.

```haskell
-- Dans :  f x = x + y
-- x est liée (paramètre de f)
-- y est libre (doit être définie ailleurs)
```

Dans cet exemple, `x` est liée car elle est introduite comme paramètre de `f`.
`y` est libre car elle n'est pas déclarée par `f` — sa valeur doit exister dans
l'environnement au moment où `f` est définie.

```haskell
y = 5

f x = x + y    -- y est libre, sa valeur est celle de l'environnement

ghci> f 3    -- 3 + 5
8
```

## Les fermetures

Une **fermeture** (*closure*) est une fonction qui **capture** les variables
libres de son environnement de définition. Autrement dit, une fermeture
« se souvient » des valeurs qui étaient en portée au moment où elle a été
créée, même si ces valeurs ne sont plus directement accessibles par la suite.

En Haskell, toute fonction lambda (ou toute fonction définie localement) qui
utilise des variables de son contexte est une fermeture. Dans l'exemple
ci-dessous, `fabriquerAdder` reçoit un entier `n` et retourne une lambda qui
capture `n` :

```haskell
-- fabriquerAdder retourne une fonction (fermeture)
fabriquerAdder :: Int -> (Int -> Int)
fabriquerAdder n = \x -> x + n
--                       ^^^^
--               fermeture : capture n de l'environnement

ajouter10 :: Int -> Int
ajouter10 = fabriquerAdder 10

ajouter42 :: Int -> Int
ajouter42 = fabriquerAdder 42
```

Chaque appel à `fabriquerAdder` produit une nouvelle fermeture indépendante,
avec sa propre copie de `n` :

```haskell
ghci> ajouter10 5
15
ghci> ajouter42 5
47
```

`ajouter10` et `ajouter42` sont deux fermetures distinctes : chacune a capturé
sa propre valeur de `n` au moment de leur création. Modifier l'une n'affecte
pas l'autre — ce qui est rendu possible par l'immuabilité de Haskell.

## Les fermetures et la curryfication

En Haskell, la curryfication et les fermetures sont intimement liées.
Rappelons qu'une fonction currifiée `f :: a -> b -> c` est en réalité une
fonction qui retourne une fonction : `f :: a -> (b -> c)`. Lorsqu'on
l'applique partiellement à un premier argument, on obtient une nouvelle
fonction — et cette nouvelle fonction est une fermeture sur l'argument reçu.

```haskell
addition :: Int -> Int -> Int
addition x y = x + y

-- addition 5 est une fermeture qui capture x = 5
ajouter5 :: Int -> Int
ajouter5 = addition 5    -- équivalent à \y -> 5 + y
```

`addition 5` produit la fermeture `\y -> 5 + y` : la valeur `5` est capturée
comme variable libre `x`. Toute application partielle en Haskell crée donc
implicitement une fermeture — c'est pour cela que la curryfication et les
fermetures sont deux facettes du même mécanisme.
